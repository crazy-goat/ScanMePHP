# Symbology roadmap

What this library encodes, what it is going to encode, and what it has decided
not to encode yet.

> These tiers are about **symbology coverage**. They are unrelated to the three
> execution tiers in `README.md` — extension, FFI, pure PHP — which are about
> how fast QR encodes and apply to nothing else.

## Shipped

Twenty-seven generators, each with a reference fixture generated by an encoder
we did not write and a decoder round trip — except the four-state postal codes,
which nothing free reads and which are gated by a substitution instead. See
`README.md` for what each one accepts.

| Family | Generators |
| --- | --- |
| Matrix | `qrcode`, `data-matrix`, `gs1-data-matrix`, `gs1-qr`, `aztec`, `pdf417`, `maxicode` |
| Linear | `code128`, `gs1-128`, `code39`, `code39ext`, `code93`, `codabar`, `itf`, `itf14`, `databar-omni`, `databar-limited`, `databar-expanded`, `databar-expanded-stacked` |
| Retail | `ean13`, `ean8`, `upc-a`, `upc-e`, `ean2`, `ean5` |
| Postal | `rm4scc`, `kix` |

## Tier 3 — closed

Closed 2026-09-03. This was the first agreed scope for v2, and it is done; the
tag now waits for the tiers below it as well.

- ~~**GS1 layer**~~ — done. `gs1-128`, `gs1-data-matrix` and `gs1-qr` all ship,
  over one derived application identifier table
  (`Generator\Gs1\ApplicationIdentifier`) and one FNC1 placement rule. The
  three differ only in how FNC1 is spelled: a symbol character, a codeword, a
  mode indicator. GS1 QR is pure PHP only — the C++ core exposes
  `encode(data, len, ecl)` with nowhere to put a mode indicator, and native
  acceleration is not growing new symbologies, so that limit is deliberate and
  written into the generator.
- ~~**Aztec**~~ — done. `aztec`, pure PHP, with the error correction percentage
  and the symbol size as caller options.

  Two things this entry got wrong are worth recording. The Reed–Solomon was
  *not* reusable: `Encoding\ReedSolomon256` is hardcoded to GF(256) — a
  256-row factor table and no log lookups in the inner loop, which is what
  makes it fast enough for QR — and Aztec needs five fields, GF(16) for the
  mode message and GF(64) through GF(4096) by layer count. Widening the tuned
  class would have cost QR's hot path for no gain, so Aztec has its own plain
  `Encoding\Aztec\ReedSolomonGf2m`.

  And the spiral was not the hard part. The hard part was that the symbol size
  turns out to be a *preference* rather than a fact, exactly as a QR mask is:
  Aztec's error correction is a floor, every symbol big enough satisfies it,
  and ten boundaries measured off zxing-cpp's own output fit no formula of the
  shape "a percentage of the data plus a constant". So the fixture pins the
  size and compares everything downstream of it. Two payloads out of forty also
  encode to different bits of the same length, and one encodes shorter here
  than in zxing — so the suite asserts modules where the streams agree and
  everywhere asserts the claim that survives a tie: never more data words than
  the oracle.
- ~~**PDF417**~~ — done. `pdf417`, pure PHP, with the column count, a row
  floor, the error correction level and the row height as caller options.

  The Reed–Solomon over GF(929) was the piece this entry expected to be hard
  and it was not: a prime field needs its own class, since over GF(2^m)
  addition is exclusive-or and here it is addition, but the class is ninety
  lines and it was right the first time it ran.

  What this entry did not see coming is that **one table cannot be derived**.
  A pattern's cluster is computable — the alternating sum of its four bar
  widths, modulo nine — but which of a cluster's 929 patterns means which value
  follows no order at all, and four candidate orderings were checked before
  accepting that. So it is measured, seeded from row indicator values this
  library states itself and grown by a bootstrap that discards any symbol
  disagreeing with what it already knows. Half the symbols get refused, and
  the refusals turned out to be informative: zxing prepends an ECI header to
  binary input, so the same bytes give a different symbol.

  The compaction search also came out better than expected. Both group
  structures being finite — forty-four digits, six bytes — means the marginal
  cost of a character depends only on its offset within its group, so an exact
  search over every possible segmentation needs fifty-eight states per position
  and runs linearly. Against zxing across 148 payloads it was never longer and
  never shorter: half identical, half the same length by another route. Three
  fixture rows are those ties and are recorded as such.

  One thing found rather than built: PDF417's rows are three modules tall, and
  making that work needed no new mechanism, because a symbol has always been
  able to state its own row heights. It is the first matrix symbology to use
  them.
- ~~**MaxiCode**~~ — done. `maxicode`, pure PHP, with the mode and — in the two
  structured modes — the postcode, country and service class as caller options.
  It was the two units of work this entry said it was, and both came out
  differently from the guess.

  The generator half was **measurement, not implementation**. Zint writes
  MaxiCode and zxing reads it, so the round trip runs between two independent
  encoders — but `write_barcode_to_image` rasterises hexagons, and the "one
  pixel is one module" assumption every other fixture here leans on is false.
  Three attempts at fitting the lattice to a raster disagreed with each other
  before the SVG turned out to state it exactly. The module map was then
  recovered by *computing* all 144 codewords — code sets, then Reed–Solomon —
  and matching each of the 974 lattice positions to the bit it tracks across a
  hundred payloads, which confirms the arithmetic and the placement together.
  Three of the four candidate interleavings match under 600 of 813 positions;
  the right one matches every single one.

  Two things could not be read that way and were measured another way. The mode
  codeword is constant across those payloads, so its six cells were found by
  exhausting the primary message's error correction: with five of its twenty
  codewords already corrupted, one more flipped module breaks decoding if and
  only if it belongs to a codeword. Exactly six cells fail. And bits 3 to 5 of
  that codeword are zero in every mode the standard defines, so nothing can tell
  them apart — recorded as undetermined rather than guessed at silently.

  The Reed–Solomon was reusable this time, which is the opposite of Aztec's
  entry: MaxiCode's codewords are six bits, `ReedSolomonGf2m` already had that
  field for Aztec's first two layer counts, and it needed no change at all. It
  moved from `Encoding\Aztec` to `Encoding`, where a shared primitive belongs.

  The renderer half needed a real division of labour rather than a new shape.
  The bullseye is three concentric rings, not modules, so it has no
  representation in a grid of light and dark cells: the symbol reports it as a
  finder region and the renderer draws it. That is why `ModuleShape::Hexagon` is
  a capability and not a hint — SVG and PNG grew hexagons, and the ASCII and
  HTML renderers refuse the symbol by name, which is the first and only time the
  shape negotiation built into `RendererCapabilities` actually declines
  something.

  Not implemented: **mode 5**, the enhanced error correction variant. Its
  secondary message splits 68 data codewords against 56 check ones and the
  interleaving is not the plain mode's; nothing available here writes one, and
  a sweep of thirty candidate splits produced no symbol the reader would
  accept. Guessing it would mean shipping a mode that cannot be verified.

## Tier 4 — in progress

Parked on 2026-09-03 so that finishing Tier 3 was a bounded job, and unparked
the same day: the v2 tag waits for every tier, not for Tier 3. Each entry is
its own unit of work, one branch at a time.

Before any of it was written, the oracles were checked rather than assumed, and
they do not cover this tier evenly. That is the fact that sets the order:

| | Reference encoder | Decoder round trip |
| --- | --- | --- |
| DataBar, all variants | zxing-cpp | zxing-cpp |
| Micro QR, rMQR | zxing-cpp | zxing-cpp |
| Telepen | zxing-cpp | zxing-cpp |
| Four-state postal | zint, via `pyzint` | **none** |
| MSI, Pharmacode, Code 11 | zint, via `pyzint` | **none** |

Two things this table is easy to misread. **zxing-cpp's writer is zint** — the
error text it raises on a malformed DataBar payload is zint's own return code —
so reaching for `pyzint` where zxing has no reader is not a second opinion, it
is the same engine through another door. It is still independent of this
library, which is all a reference fixture requires, but the bottom two rows are
checked once rather than twice and should say so where they land.

And no free decoder reads the bottom two rows at all: zbar covers DataBar but
none of them, and the ones that do are commercial. So those two need the
substitution `AGENTS.md` describes rather than a skipped round trip. The
strongest available stand-ins are known: USPS publishes an official encoder
validation file for the Intelligent Mail barcode, which is the issuing
authority rather than a reader; RM4SCC, KIX and Australia Post have worked
examples in their standards; Pharmacode is binary arithmetic and inverts
without any knowledge from the encoder. MSI and Code 11 are the Codabar problem
again — check-digit variants in circulation disagree — and the precedent there
is to ship no option and assert that it does not exist.

- ~~**GS1 DataBar Omnidirectional**~~ — done. `databar-omni`, pure PHP, with
  the truncated height as the single caller option.

  There was no table to transcribe, which is the whole character of this
  symbology: a data character is a *value*, and its eight element widths are
  that value's index into an enumeration of every legal combination of four
  bars and four spaces. So what needed verifying was a function, and a function
  is wrong across a range rather than in one place.

  Everything it is built from was measured rather than remembered, and two of
  those measurements overturned a first attempt. The bars carry no "at least
  one narrow element" rule and the spaces do — backwards, it changes how many
  combinations sit in each bucket and shifts every value past that point. And
  the inside characters interleave the other way round from the outside ones,
  space first rather than bar first. Each of the four character positions was
  fitted separately against the oracle and each admits exactly one of the four
  possible orderings; the group tables were recovered by counting group sizes
  out of the oracle's own symbols, which come to 161, 800, 1054, 700 and 126.

  Two things turned out not to need a table at all. The checksum weights are
  the powers of three modulo 79 — reference implementations ship them as
  thirty-two literals, which is the same numbers spelled the way most likely to
  acquire a typo. And there is no check character anywhere in the bars: the two
  finder patterns *are* the checksum, the left one's index being it over nine
  and the right one's the remainder. The nine finder patterns themselves are
  the one measured table, because they enumerate nothing.

  The right half of the symbol is the left half's construction mirrored whole.
  Laying it out left to right produces a symbol that scans and carries a
  different number, which is the failure this fixture exists to catch.

  One property was asserted, failed, and turned out to be false rather than
  broken: changing any one digit does *not* have to move a finder. Eleven of
  the thirteen do; the checksum is modulo 79 and two of them land back where
  they started. What replaced it is a claim that holds — two of the eighty-one
  finder pairs are never drawn.

- ~~**GS1 DataBar Limited**~~ — done. `databar-limited`, pure PHP, no options.

  "A second encodation of the same GTIN in fewer modules" is true and turned
  out to be almost the whole of what it shares with Omnidirectional. The
  enumeration function is the same; every number fed to it is different.
  Characters are seven bars and seven spaces rather than four and four, the
  narrow-element rule is on the bars rather than the spaces, the value counts
  up through its bars rather than its spaces, and the seven character groups
  begin at 0, 183064, 820064, 1000776, 1491021, 1979845 and 1996939 — found by
  binary search on where the oracle's symbols change shape, since none of them
  follows from anything.

  The finder is the checksum again, but with eighty-nine patterns and one per
  residue, nothing skipped. Each splits into two halves of nine modules that
  the same enumeration generates, so the table is stored as pairs of indices
  rather than 1246 widths; which eighty-nine of the 441 possible pairs the
  standard uses follows no local rule that could be found — element widths,
  adjacent sums and counts of wide elements all take the same values inside the
  chosen set as outside it — so that part is measured, one residue at a time.

  Generalising the enumeration for it turned up something about the family that
  the Omnidirectional work had not needed to know: the walk's ceiling
  correction is a first-order one, exact only while two elements cannot both
  overflow at once. In two of Omnidirectional's inside groups they can, which
  is why the standard's tables carry a count of reachable combinations rather
  than leaving it to be derived. Deriving it — which the first generalisation
  did — changes the bars for 432 of the 1597 inside characters, all of them
  still scannable, as other numbers. The existing fixture caught it.

  The one thing Limited refuses that Omnidirectional does not: indicator digits
  above 1. Two characters of 2013571 values reach 1999999999999 and stop.

- ~~**GS1 DataBar Expanded**~~ — done. `databar-expanded`, pure PHP, no
  options.

  It does carry general AI data, and that turned out to be the smaller half of
  the job. The larger half is that almost nothing about it could be read off
  the other two: the value space is twelve bits rather than a mixed radix, the
  narrow-element rule sits on the odd *positions* of a character rather than on
  its bars or its spaces (the colour depends on where the character sits, since
  the symbol is one alternating run from guard to guard), the finder is not the
  checksum but a function of the symbol's length, and the checksum weights are
  3^(8k+j) mod 211 with k out of a per-length table that scrambles below
  fourteen characters and is the identity above it. Each of those was measured:
  the character table by driving the last data character through all 4096
  values, the finder sequences one length at a time, the weights by solving a
  linear system over GF(211) for each length.

  The encodation cost the most and gave the least away. The clue that unlocked
  it was a carry landing on 4000 instead of 4096 — decimal fields are packed
  ten bits per three digits, not as binary integers, which is why the AI 01
  item reference is 40 bits and not 44. Numeric mode then turned out to be
  seven bits per digit pair rather than eleven; eleven agrees with every
  general-purpose symbol because the method's five-bit prefix pads it to the
  same place, and only the AI 01 method's field, which starts at bit 48,
  separates the two. Two further rules are invisible when wrong: an FNC1
  written from alphanumeric or ISO 646 mode returns the field to numeric, and a
  final lone digit may be four bits instead of seven when that saves a symbol
  character.

  The mode-switch thresholds are asymmetric in a way no reasoning about cost
  predicts, and two of the three cases that pinned them were ties the encoder
  breaks by rule rather than by size. Leaving ISO 646 for a digit run takes ten
  digits mid-field, or four when everything after the digits could be said in
  alphanumeric mode; leaving it for a run of capitals takes ten, or five at the
  end of the data.

  Deliberately not implemented: the fourteen compaction methods for
  variable-measure trade items, where AI 01 is paired with a weight, a price or
  a date. Those payloads go through the AI 01 method instead — a correct symbol
  saying the same thing, one or two characters wider than the narrowest a
  standard-complete encoder draws. They are a size optimisation over a narrow
  set of AI combinations, and each carries its own field layout and value
  ranges to get wrong.

- ~~**GS1 DataBar Expanded Stacked**~~ — done. `databar-expanded-stacked`,
  pure PHP, one option: how many character pairs a row holds.

  The encodation is the linear one, with a single change that turns out to
  reach everywhere: a row may not be left holding one character, so some
  payloads take an extra character of padding — which moves the character
  count, the variable length bits and therefore the checksum. It has to be
  decided before the bit stream is written rather than while folding.

  Three things about the layout were measured because each draws a plausible
  symbol when guessed wrongly: rows are cut at character boundaries and not at
  pair boundaries, so a row can end on a finder with no character after it;
  every second row is drawn mirrored; and a row of exactly two characters is
  the exception that is drawn forwards anyway, one module to the right. A
  three-character row in the same position is mirrored like any other, which is
  what says the exception is about the two-character row rather than about the
  last row.

  The separator is three module rows — the complement of the row above, an
  alternating line, the complement of the row below — except inside a finder's
  columns, where the complement would print the finder again upside down. There
  it alternates, carrying a running state in from the module before the finder,
  which is why two finders in one row can come out in opposite phases.

  **Open question worth recording:** rows of an odd number of character pairs do
  not read back. Twelve layouts were constructed for them — mirroring by row
  parity, by the row's first pair, not at all; finder orientation by position in
  the row and by position in the symbol — and zxing-cpp read none of them, while
  it reads every even width under every one of those layouts. The reference
  encoder only draws two pairs per row, so there is nothing to compare against.
  Rather than emit symbols nothing has read, the option refuses odd widths; if
  an encoder that draws them turns up, this is the first thing to revisit.
- **Four-state postal codes** — ~~RM4SCC~~, ~~KIX~~, Intelligent Mail, Australia
  Post. The machinery that was already written and unused is now used:
  `AbstractRenderOptions::resolveRowHeights()` scales row heights
  proportionally precisely because a four-state code's meaning is the ratio
  between ascender, tracker and descender, and RM4SCC is the first symbology to
  need it.

  The reference path was built ahead of the first of them:
  `tools/four_state.py` draws through zint and reads the four states back out
  of the SVG geometry, because zint reports a rectangle and not a state. That
  reading is the tooling's only real claim, so it is measured rather than
  asserted — zint's own DAFT symbology takes a state string verbatim, which
  makes it a fixture for the reader (`composer reference:four-state-check`).
  The four payloads their standards publish come back at the lengths those
  standards give: 30 bars for RM4SCC, 44 for an eleven-character KIX, 65 for
  Intelligent Mail, 37 for an eight-digit Australia Post. Each symbology still
  brings its own fixture and its own substituted round trip.

  **RM4SCC is done.** `rm4scc`, pure PHP, no options. It turned out to have no
  table in it at all: six four-bit patterns carry two bits each — two ascenders
  and two descenders per character, which is the symbology's error detection —
  and a character's place in the alphabet is its pair of them read as a base-six
  number. Every published RM4SCC table is that arithmetic written out. The check
  character is the same arithmetic over the sums, with the nibbles worth 1 to 6
  rather than 0 to 5; the two conventions disagree exactly when a sum is a
  multiple of six, which is a six-character postcode, so it is asserted with a
  property that only the right one satisfies — appending the character worth six
  leaves the check character alone.

  The substituted round trip is the part with no precedent here. There is no
  decoder to hand the PNG to, so the rendered image is measured back into state
  letters — bars found as runs of dark columns, each one's state read from which
  edges of the symbol's ink its column reaches — and compared with what zint
  drew. That gates everything after the module grid: the PNG encoder, the module
  size, the quiet zone, the three row heights. It buys no second opinion on the
  bars themselves, which is why it is declared in
  `DecoderRoundTripTest::NO_STANDALONE_READER` with a test that fails the day
  zxing-cpp learns to read one.

  Fifty characters is the payload ceiling, and it is zint's rather than the
  standard's: past it we would emit symbols nothing has ever agreed with.

  **KIX is done too.** `kix`, pure PHP, no options — and the smallest symbology
  in the library, because it is RM4SCC's alphabet with the envelope taken off:
  no start bar, no stop bar, no check character. A KIX symbol is its characters
  concatenated and nothing else, which is asserted directly, since every mistake
  available here is a mistake of addition.

  The alphabet being shared is measured, not assumed — the two fixtures were
  drawn independently through zint and agree character for character — so it was
  lifted into `Generator\FourState\Alphabet` and RM4SCC now keeps only what is
  its own. Two copies of a base-six derivation are two chances for one of them
  to drift, and a drifted copy still draws thirty-six legal characters;
  `KixTest` asserts the two still agree.

  What KIX costs its readers is worth stating, because a caller reaching for a
  postal code tends to assume the symbology checks something. It does not: a
  dropped or added character produces another legal symbol saying something
  else, and the only integrity left is the per-character two-of-four parity,
  which catches a misread bar rather than a misread symbol. Sorting machines
  read KIX beside an address they can compare it against. The quiet zone is
  load-bearing in a way it is not in RM4SCC — with no start pattern, white space
  is the only thing marking where the first character is — so it stays on all
  four sides. Eighteen characters is the ceiling, and this time it is the
  specification's, not zint's.

  The substituted round trip is now one test over the family rather than one per
  symbology: the next four-state code adds a row to `fourStateProvider()` and
  cannot quietly decide it did not want the gate.
- **Micro QR and rMQR** — separate symbologies with their own version tables,
  not a mode of `qrcode`.
- **Minor linear codes** — MSI, Pharmacode, Code 11, Telepen. Cheap to add and
  correspondingly rare; the cost is API surface, not encoder complexity.

## Tier 5 — standard coverage on what already ships

Everything below is a piece of a standard that a generator in the Shipped table
does not implement. None of it is a wrong symbol: each entry either costs
modules a standard-complete encoder would not spend, or refuses a payload the
symbology could have carried. They are collected here rather than filed against
their own entries because they share a shape — the encoder was finished against
what the round trip could prove, and these are what the round trip never asked
about.

Ordered by what it costs to leave alone, which is not the order they were
written in.

- **#201 — the suite segfaults with the extension loaded.** The only entry here
  that is a defect rather than a gap, and the only one that hides other
  failures. `ci.yml` runs the suite a second time under
  `php -d extension=…/scanmeqr.so`, and that pass corrupts memory and crashes on
  roughly half of all runs — on `main` as much as on any branch, so it predates
  every symbology in Tier 4. It is `continue-on-error: true` today, which means
  a real regression introduced by an extension change would look exactly like
  the crash that is already there.

  Nothing about it is diagnosed. The suspicion is the lifetime of a symbol's
  buffer across the ext boundary, since the pure-PHP and FFI passes are clean
  and only the loaded-extension pass crashes, but that is a place to start
  looking rather than a finding. Whatever else this tier does, this one comes
  first: until it is fixed the extension has no honest CI signal.

- **QR chooses no mode.** `Encoder.php` calls the data encoder with
  `Mode::Byte` and nothing else — twice, once for plain QR and once for GS1 QR.
  `Encoding\DataEncoder` already implements numeric, alphanumeric and Kanji
  compaction; `Mode::Numeric`, `Mode::Alphanumeric` and `Mode::Kanji` appear
  nowhere in the library outside the class that implements them.

  This is the widest of the gaps in ordinary use, because it is the default
  symbology and the numbers are large: a numeric payload takes eight bits a
  digit where the standard spends three and a third, and a payload of capitals
  and digits takes eight where it should take five and a half. A URL in
  uppercase or a run of digits therefore reaches a version two or three higher
  than it needs, and past the version where the character count field widens it
  can be more.

  The work is not the compaction — that exists — it is segmentation: choosing
  where to switch modes, which is the same optimal-partition problem PDF417's
  entry solved exactly and cheaply. The one thing not to assume is that the
  cost model transfers; QR's mode header and character count field are
  version-dependent in a way PDF417's groups are not.

- **Data Matrix is ASCII only.** `AsciiEncodation` is complete and its own
  docblock is honest about being the only scheme. C40, Text, X12, EDIFACT and
  Base256 are all absent. ASCII packs two digits into a codeword and one letter
  into a codeword, so digits are already optimal and text is not: C40 and Text
  put three characters into two codewords, which is a third off any payload
  that is mostly letters. Base256's absence costs more per byte — binary data
  goes through ASCII's upshift, a codeword and a half per byte — and it is also
  the scheme that would let a Data Matrix carry arbitrary bytes at all without
  the caller pre-encoding them.

- **PDF417 emits no ECI header and no macro block.** Both are stated in
  `Encoding\Pdf417\HighLevelEncoder`'s docblock. The ECI half is the smaller
  one and already half-known: the PDF417 entry in Tier 3 found that zxing
  prepends an ECI header to binary input, which is *why* half the bootstrap
  symbols were refused, so the encoder that would have to be matched has
  already been observed doing it.

  The macro block is the larger job and the one with a capability behind it.
  It is how a message longer than one symbol is split across several — a
  segment index, a file ID, and optionally a file name, a segment count and a
  checksum, so a reader reassembles them. Without it the answer to a payload
  over 925 codewords is that it does not fit, rather than that it takes two
  symbols.

- **Aztec has no FLG(n).** Recorded in `Encoding\Aztec\HighLevelEncoder`'s
  docblock as not implemented, with the reason that nothing in the library asked
  for it. FLG(n) is Punct code 0, and it is the single mechanism by which an
  Aztec symbol says anything about its own bytes: FLG(0) is FNC1, so a GS1
  Aztec is impossible without it, and FLG(1) through FLG(6) carry an ECI
  designator, so a non-ASCII payload can only be read by a decoder that guesses
  the encoding correctly.

  Note the shape of that: this is the one entry where the missing piece would
  add a symbology rather than shrink a symbol. `gs1-aztec` is not on any tier
  list, and it is FLG(0) plus the FNC1 placement rule the GS1 layer already
  has.

- **MaxiCode mode 5 is unimplemented.** Kept from the Tier 3 entry rather than
  restated, because the reason it is open has not changed and is not effort:
  its secondary message splits 68 data codewords against 56 check ones with an
  interleaving that is not the plain mode's, nothing available here writes one,
  and a sweep of thirty candidate splits produced nothing the reader accepts.
  Mode 5 is mode 4 with enhanced error correction, so what is missing is
  robustness on a non-carrier payload, not a payload that cannot be said at
  all. It stays open until an encoder that writes one turns up; guessing at the
  interleaving would ship a mode with no way to know it is right.

- **DataBar Expanded's fourteen compaction methods.** For variable-measure
  trade items — AI 01 paired with a weight, a price or a date. Those payloads
  encode correctly today through the general AI 01 method, one or two symbol
  characters wider than the narrowest a standard-complete encoder draws. Last
  on this list on purpose: it is the narrowest set of inputs of anything here,
  and each of the fourteen carries its own field layout and value ranges to get
  wrong, so the ratio of risk to modules saved is the worst in the tier.

## Tier 6 — renderer coverage

The last tier, and the only one about neither symbologies nor the standards
behind them. Tier 5 is what the shipped generators do not yet say; this is what
the renderers cannot yet draw.

- **Hexagons in the HTML renderers.** MaxiCode is refused by `html-div` and
  `html-table` today, and the reason is scope rather than capability — CSS
  draws a hexagon with `clip-path: polygon(...)`, offsets every odd row with a
  margin, and draws the bullseye's rings with `border-radius` and a border. It
  would work and it would scan.

  What stops it is that `HtmlRenderer` is built around one element per module
  in a grid, with the quiet zone collapsed into a handful of sized blocks. A
  hexagonal lattice is a second, unrelated rendering path inside the same
  class — about the size of the job the PNG one was — and `ModuleShape::Hexagon`
  already reports the refusal honestly, so nothing is silently wrong in the
  meantime.

  The ASCII renderers are a different matter and are **not** on this list. A
  terminal is a fixed raster of character cells with no way to offset a row by
  half a cell, and the bullseye is three circles; anything drawn there would be

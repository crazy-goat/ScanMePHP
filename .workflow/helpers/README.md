# Knowledge Base (`.workflow/helpers/`)

A persistent knowledge base so lessons learned carry over to future tasks.

## Files

- `faq.md` — recurring pitfalls and their solutions. Ids `FAQ-NNN`.
- `decisions.md` — project decisions with rationale. Ids `DEC-NNN`.
- `README.md` — this file.

## Entry format

Every entry is a `###` heading followed by a single-line HTML comment with
front matter, then the body:

```markdown
### Title goes here

<!-- id=FAQ-001, date=2026-04-01, tags=phpunit ports, trigger=test failures with "Address already in use", status=active -->

Body paragraph(s)...
```

Front matter fields:

| field   | required | meaning                                                        |
| ------- | -------- | ------------------------------------------------------------- |
| `id`    | yes      | Unique id, `FAQ-NNN` / `DEC-NNN`                              |
| `date`  | yes      | `YYYY-MM-DD` the entry was written                             |
| `tags`  | yes      | Space-separated tags for the tag index                         |
| `trigger` | yes    | One-line description of when this entry applies                |
| `hits`  | no       | How many times this entry has been relevant (manual count)     |
| `status` | yes     | `active` or `stale` (stale entries are listed by kb-lint)     |

## Tag index

Every file opens with a generated tag index mapping tags to entry ids. It is
regenerated by `php bin/kb-lint.php --fix`. **Do not edit it by hand.**

A subagent loads the index, picks the tags matching the files in its diff, and
reads only those `###` entries. Reading 300 lines of FAQ for a two-file change
is exactly what the index exists to prevent.

## Single-writer rule

Only the **main session**, at the end of a cycle (workflow step 14), writes to
`.workflow/helpers/`. `coder` and `review` subagents **propose** candidate
entries in their report — title, tags, trigger, one paragraph — and the main
session decides what lands. Two writers produced duplicates, unlabelled entries
and a file that had to be read in full; a subagent that appends to the knowledge
base itself is doing the wrong thing.

## Prefer a gate over an entry

If a regression test, PHPStan rule or lint rule could catch the class of
defect, add the check. The knowledge base is a buffer for what cannot be
automated yet, not a destination.

## Decay

An entry is `stale` when the code it describes has changed enough that the
entry no longer matches reality, or when the check it recommended has been
added and makes the entry redundant. `php bin/kb-lint.php` lists stale entries.
A stale entry should either be updated and flipped back to `active`, or
removed.
